# 2026-10-06: Hetzner cpx62, OpenVox 8.16.0 and 9.0.1

## Setup

- **Server:** Hetzner cpx62, 16 shared AMD vCPUs, 31 GB memory, AlmaLinux 10.2,
  installed with ovadm. Java 21.0.12 for both versions. OpenVox Server 8.16.0
  (agent 8.29.0), then upgraded in place to 9.0.1 (agent 9.0.0, JRuby 10.1.2)
  with `ovadm::upgrade`.
- **Load generator:** Hetzner ccx23, 4 dedicated vCPUs, Ubuntu 24.04, agent
  8.29.0, on the same private network.
- **Workload:** [`site.pp`](../site.pp) with puppetlabs-apache 13.4.0,
  puppetlabs-mysql 17.3.0 and puppetlabs-firewall 8.6.0: 1,511 resources,
  a 1 MB catalog.
- **Procedure:** each configuration got 5 minutes of warm-up at 16
  concurrent requests, then 2 minutes at each level. The `-warm` runs repeat
  the levels straight after, on a server that had been under load for about
  18 minutes.
- **Configurations:**
  - `default`: the packaged settings, 4 JRubies and a 2 GB heap, with
    `environment_timeout` 0.
  - `tuned`: the `openvox_tune::tune` plan's recommendation, 15 JRubies, an
    8192 MB heap and a 2048 MB code cache, applied by the `openvox_tune` class
    from node data.
  - `envcache`: `environment_timeout = unlimited` in `[server]`.
  - `ov9-`: the same on OpenVox 9.0.1.

The runs went in the order the tables below appear. There was no CPU steal
during any of them.

## Summary

Catalogs per minute at 32 concurrent requests, and p95 latency:

| Configuration | OpenVox 8.16.0 | OpenVox 9.0.1 |
|---|---:|---:|
| Packaged defaults | 89 (22.4 s) | not run |
| Packaged defaults, `environment_timeout` unlimited | 105 (18.8 s) | 99 (20.5 s) |
| Tuned, `environment_timeout` unlimited, warmed up | 300 (7.1 s) | 283 (7.6 s) |

- With the packaged defaults, throughput stops at 4 concurrent requests and
  the server's CPU stays about a third busy. Every request beyond 4 waits
  for a JRuby.
- With the recommendation, throughput rises with concurrency until the CPU
  is full at 16 concurrent requests, and compile times stay about where
  they are with 4 JRubies.
- Caching environments adds about 20%: compiles stop re-reading the code.
- 15 JRubies take longer to warm up than 4, since each warms up on its own.
  Under full load, compiles took 8 to 12 seconds for the first 5 minutes
  after the restart and settled after about 15 to 20 minutes. See the
  per-minute compile times below. The `tuned` run, without environment
  caching, was measured only while still warming up.
- OpenVox 9.0.1 was 5 to 6% slower than 8.16.0 on this workload, with or
  without tuning, and the tuning gain was the same.
- The tuned server used about 11 GB of memory, against 3.4 GB. The heap
  peaked at about 70% of 8 GB, and young GC took about 1% of the time,
  with no old-generation collections; 512 MB per JRuby was enough for this
  code.

## Limits

- One run per configuration, on shared vCPUs.
- Catalog compiles only: no fact uploads, reports or file serving.
- One node's catalog, compiled over and over; a real fleet's catalogs vary.
